## 1. Rules

- No SAP BTP platform: no Cloud Foundry, MTA, HANA Cloud, XSUAA, app router or Destination service. SAP CAP is the framework.
- One database: SQLite (`backend/db/medilink.sqlite`; in memory for tests). No other database, no database server, no Docker.
- One login: MediLink accounts (`srv/auth.js` + `srv/lib/accounts.js`) in every profile; no mocked users. Only pharmacists, approvers and the admin sign in; couriers use per-delivery links.
- SAP AI Core, SAP Build Process Automation, SAP Alert Notification and the SAP Business Accelerator Hub sandbox are optional adapters, off by default, switched on by env only. MediLink must work fully without them. Never add paid services.
- Never print, log or commit secrets. Config from env (`backend/.env`, git-ignored; template `backend/.env.example`). `npm run dev` generates a development `.env`; production never creates secrets or demo users by itself.
- Patient names never enter MediLink; patient refs are `SHA-256(PATIENT_REF_HASH_SALT:mrn)` hashed at the source.
- All seed data is synthetic and stays labelled as such.
- Tests that start a server or child process use a free port, never a fixed one.
- Run `npm test` at the repo root after every change. All of it must stay green.

## 2. Architecture

| Process | Code | Talks to |
|---|---|---|
| MediLink: CAP 10 (Node.js) + UI + WebSocket | `backend/`, `frontend/` | SQLite file; matcher; MediSoft (OAuth); SMTP; optional SAP services; OpenRouteService, Open-Meteo |
| Matcher: FastAPI + OR-Tools CP-SAT `POST /rank` | `matcher/` | Called by CAP with `X-Matcher-Token`; optional LLM for plan wording |
| Mock MediSoft HIS (demo) | `mock-medisoft/` | OAuth 2.0 + PKCE server, `/stock`, `/schedule` |
| DB connector (at a hospital) | `connector/` | Reads the hospital's own DB (any SQLAlchemy URL), pushes to `POST /ingest` |
| Courier simulator (demo) | `simulator/` | Lists links as admin, acts through `/courier/*` |
| Courier's phone | `frontend/courier.html` | `/courier/*` with `Authorization: Courier <token>` |

Request path: CAP custom auth (`srv/auth.js` → `accounts.authenticate`: Bearer JWT with a `Sessions` row, Basic for scripts,
single-use ticket on WebSocket upgrades) → `@requires` / `@restrict` in `services.cds` → thin handler → `lib/`.

## 5. Decisions

| Decision | Why |
|---|---|
| SQLite file only, one CAP process | Zero set-up, free hosting; enough for pilot scale. Writes are serialised (one connection), which keeps the audit chain gap-free |
| MediLink accounts only; portal = pharmacist, approver, admin; `system` API-only | No BTP; couriers are not hospital staff |
| Courier = capability link per delivery (token in the URL fragment, SHA-256 + AES-GCM at rest, 24 h TTL, revoked on cancel / recall / reissue) | No courier accounts; W3C TAG capability-URL practice |
| WebSocket sign-in by single-use 30 s ticket | Tokens in URLs end up in proxy logs |
| Optional SAP services behind env switches with a built-in fallback each | Runs fully without any SAP account |
| One outbound alert channel: Alert Notification, else SMTP, else console; one digest per hospital per check | Simple routing; per-hospital recipients |
| Low stock = usable units ≤ reorder level (hospital level, else drug default, else not watched); expiry alerts only for the tightest tier | No alert storms; one alert per condition, escalates when worse |
| Journeys derived on every read, never stored; tasks come from journeys | A card and its journey never disagree |
| Idempotency: `Idempotency-Key` + user + action, stored responses replay; still-running key → 409 `ACTION_IN_PROGRESS` | Double taps |
| Rate limits, login throttle, WS tickets, ETA throttle in memory (`shortcut:` comments) | Right for one process; move to a shared store before scaling out |
| Received stock reconciled by heuristic (F22) | No MediLink reference reaches the hospital's system |

## 6. Known limitations

- **No migrations.** New columns need `npm run db:reset`, which deletes all data. Add a migration path before real data.
- Single instance only: rate limits, login throttle, WS tickets and the ETA throttle are per process (`shortcut:` in `ratelimit.js`, `accounts.js`, `courier.js`, `tracking.js`).
- Courier geolocation needs HTTPS and pauses in background tabs; the logger's temperature is the source of truth; GPS-only fixes never count towards the trace.
- Cancelling a request does not cancel a running SAP Build Process Automation instance.
- Monitoring: no snooze, no days-of-cover thresholds; digests go out per check (not daily); plain-text email; the inbox shows the newest 200 rows.
- FR-13: the `/me` shortfall journey shows the affected-patient count, not the booking list.
- A `journey.updated` pushed to all approvers still shows **Approve** to the one who already signed; tapping it says "A second person must sign". `GET /me/home` is exact.
- CAP registers dotted events under their last segment, so `ws.js` emits `updated` for `journey.updated` (`ws-filter.test.js` fails if CAP changes this).
- English only; Kannada / Hindi bundles still need translating.
- Not measured on the SQLite file (perf numbers are in-memory). Linux not run in the original sessions; run `npm test` on the target host.

## 8. How to continue

1. Merge the frontend; run `npm test`, `npm run demo` and `npm run demo:experience` (fresh database); update §3 UI status and §4 counts.
2. Add schema migrations before any real data (today `db:reset` is the only path).
3. Deploy once per [`docs/HOSTING.md`](docs/HOSTING.md) on Linux; test a backup restore; measure performance on the SQLite file.
4. Verify against real accounts: SMTP, `ORS_API_KEY`, then each optional SAP integration ([`docs/SAP_INTEGRATIONS.md`](docs/SAP_INTEGRATIONS.md)).
5. Cancel the BPA instance when a request is cancelled (only if BPA is used).
6. Before running more than one process: move the `shortcut:` in-memory stores to SQLite.
7. Translate `backend/_i18n/messages.properties` to `messages_kn.properties` and `messages_hi.properties`.
8. Anchor the audit chain (periodically email or HMAC the head hash), audit §H item 10.
